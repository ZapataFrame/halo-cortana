# Implementación inicial del visor y LLM local

Fecha: 2026-10-07. Responsable: Codex. Trabajo autorizado por «Okey, a trabajar». Alcance: H-01…H-12 con aceptación técnica/limitaciones individualizadas en la roadmap. **El holograma físico y la entrega A+B completa siguen pendientes.**

## Entorno y decisiones

- CachyOS/Linux; Node 22.22.2, npm 10.9.7, RAM total observada 15 GiB; Blender no disponible.
- LAN del PC: `192.168.1.66`. Servidor único en TCP 3000, frontend y API del mismo origen.
- Dependencias instaladas: Three 0.186.1 y Vite 8.3.3, compatibles con el runtime. Lockfile presente. Instalación informó cero vulnerabilidades para ese árbol y momento.
- Modelo: CesiumMan, © 2017 Cesium, CC BY 4.0. GLB original de 438044 bytes, 4672 triángulos, un clip/skin y ninguna URI externa/extensión obligatoria. Ficha/hash/licencias en `public/models/README.md`.
- Quaternius se investigó primero; el flujo público de descarga no entregó un archivo utilizable. CesiumMan evita conversión/Blender y cumple cuerpo humanoide de internet. Modelo provisional sin aprobación estética del propietario.
- Ollama ya instalado con `phi4-mini:latest`, 3.8B Q4_K_M, archivo de modelo reportado 2491876774 bytes. Servicio `/api/ps` observó contexto 4096 y `size_vram: 0`: ejecución en CPU, sin atribuir rendimiento a la RTX 3050.
- Selección técnica D-17…D-21 registrada. H-19 separa identificación del celular/caja/hora de la preparación PC. Las pruebas físicas conservan su criterio y no se cierran por una captura PC.

## Entregables existentes

`src/viewer.js` carga un humanoide, normaliza su tamaño tras aplicar la primera pose del clip y mantiene cámara ortográfica con resize. Material blanco/gris y animación incorporada lenta. Fondo de página, escena y renderer negro; sin suelo, grid, skybox ni HUD inicial.

Calibración: espejos aplicados en ejes de pantalla después de rotar, con dos grupos Three separados; el patrón SVG utiliza el mismo orden. Esta corrección final pasó dos pruebas geométricas; las capturas previas con rotación/espejos predeterminados conservan su validez visual.

Calibración: tamaño/X/Y, vista del cuerpo, rotaciones 0/90/180/270, espejos independientes, contornos triangulares, patrón F asimétrico, reset y almacenamiento local versionado. Panel accesible tocando esquina superior izquierda; ocultarlo también apaga patrón. Fullscreen por gesto y alternativa manual de mantener pantalla despierta para HTTP LAN.

`/control` contiene vista previa, conversación, información del proveedor, URL de pantalla externa y ajustes. `POST /api/chat`, `/api/cancel` y `/api/reset` restringidos a loopback/Host local/Origin correspondiente. Máximo 2000 caracteres, seis pares recientes, una petición activa, timeout 60 s, IDs idempotentes y descarte de respuestas canceladas. No se almacenan pares incompletos. Respuestas como texto, nunca HTML ejecutable.

El backend usa Ollama real. Adaptador OpenAI Responses implementado con clave exclusivamente en servidor; **sin solicitud real a OpenAI, clave creada, facturación activada ni extracción de sesión**. Configuración de ejemplo sin secretos. El estado público expone solamente `sessionId`, `revision`, `phase`; no texto ni historial. Visor consulta cada segundo y conserva figura cuando no obtiene estado.

## Verificación ejecutada

### Build y pruebas

- `npm run build`: exitoso, 14 módulos. Bundle final aproximadamente 640.43 KB (163.22 KB gzip), CSS 7.62 KB. Aviso por chunk >500 KB; conservado como límite conocido de la dependencia 3D, sin CDN.
- `npm test`: **11/11** exitosas en ejecución final. Casos: datos corruptos/almacenamiento denegado, límites y versión; tres recuperaciones de calibración; entrada inválida/JSON corrupto/tamaño; Origin/Host y rutas privadas; cancelación sin historial parcial; idempotencia; timeout/error sin secretos; seis pares y reset; espejos en ejes de pantalla tras rotaciones y desplazamiento independiente.
- El sandbox bloqueó la primera ejecución de pruebas con sockets; se repitió con autorización para puertos locales. Un caso inicial de Host falló porque `fetch` sustituyó el encabezado; se corrigió la prueba para usar HTTP directo y pasó. No se ocultó el fallo ni se contó la ejecución inicial como éxito.
- `GET http://192.168.1.66:3000/hologram`: **200** desde PC. `POST /api/chat` por esa IP: **403**. No equivale a acceso desde el celular.
- Documentación: verificados 8 documentos, enlaces locales, bloques de código, 20 tareas H sin ciclos, un único AGENTS y GLB compilado restaurado con hash idéntico. Historial de pruebas reiniciado; `/api/info` confirmó proveedor listo y timeout 60000 ms.
- Git: `git status` devolvió `fatal: not a git repository`; no se creó ni afirmó un commit.

### Presentación digital

Inspección en navegador de la app: modelo cargado, cuerpo completo, negro y panel de control renderizados. Capturas locales:

- `evidence/hologram-desktop.png`: 1280×720.
- `evidence/hologram-portrait.png`: 749×844 efectivos. Se solicitó 390×844 al navegador, pero la superficie visible acabó en 749 px; no presentar esta captura como un teléfono de 390 px.
- `evidence/hologram-asset-error.png`: 749×844, negro completo. Se retiró temporalmente **solo la copia compilada** del GLB para provocar 404 real, se observó `data-status=error`, se capturó y se restauró el archivo inmediatamente después.

Pillow muestreó cinco coordenadas por captura: `(5,5)`, `(w−6,5)`, `(5,h−6)`, `(w−6,h−6)`, `(w/8,h/2)`. Todas dieron **RGB (0,0,0)**. La captura de error contiene exclusivamente negro. El fondo inicial está definido antes del script en HTML; falta una captura identificada inequívocamente como `loading` para cerrar toda la evidencia H-05.

Navegador: rotación 90°, espejo horizontal y vertical recuperados en **tres recargas reales**, patrón activable y reset/restauración verificados. Las interacciones automatizadas con rangos no cambiaron su valor; no se cuentan como prueba de escala/X/Y. La lógica y persistencia de magnitudes están cubiertas por pruebas; falta comprobar esos controles manualmente. No se tomó una captura del patrón reflejado físicamente.

Se observaron contadores instantáneos entre 1–2 FPS con navegador en segundo plano y 86–99 al interactuar. **No constituyen una mediana de 60 s ni un benchmark móvil.** No afirmar cumplimiento de 30 FPS/dispositivo con esas muestras.

### Respuestas reales y recuperación

| Recorrido | Entrada/resumen | Resultado | Tiempo |
|---|---|---|---|
| API Ollama directa, primera carga | Saludo breve en español | Respuesta generada; carga de modelo 10.66 s. | Total 23.75 s |
| Backend inicial, timeout 30 s | Pregunta sobre Pepper’s Ghost | HTTP 504 real; se conservó el visor. | 30 s de límite |
| Backend, timeout 60 s | «Soy Diego. ¿Qué es Pepper’s Ghost?» | Explicación nueva en español. | 47.091 s |
| Backend, contexto | «¿Cómo me llamo?» | «Tu nombre es Diego.» | 5.353 s |
| Panel PC, tercera pregunta | Ángulo inicial del reflector | Respuesta generada visible, proveedor/modelo/latencia. | 19.1 s mostrados |
| Backend, seguimiento | «Repite mi nombre, por favor.» | «Tu nombre es Diego.» | 6.923 s |
| Backend real, cancelar y recuperar | Cancelar consulta en `processing`; luego nueva consulta | Cancelada: 499 y `idle`; siguiente: 200 y `responded`. | Nueva respuesta 22.277 s |

La última petición de recuperación pidió «lista» y el modelo devolvió una enumeración: prueba transporte/recuperación, **no calidad de seguimiento de instrucciones**. El modelo puede interpretar mal solicitudes; no se han medido precisión general ni optimizado prompts. Las respuestas no ejecutan herramientas ni cambian mundo. No promediar primera carga y consultas calientes como una única promesa de latencia.

El límite inicial 30 s falló en CPU: se acortó prompt/salida local (48 tokens) y se elevó timeout a 60 s. No hay reintentos automáticos. El seguimiento de backend confirma memoria contextual; no sustituye un ensayo completo de UI/móvil.
